# M3の残り確認 — 個数と連続操作（2026-09-25）

入口プレイ（`?play=open`）で、要件のP-05（10分の実操作）と、12〜24個（M3）・60個（M4のサンドボックス上限）の描画負荷を確認した。

## 見つけて直した不具合

融合が短時間に連続すると、見た目用の「塊（lobe）」が6つ以上になり、シェーダーの配列（5つ）を超えて描画ループ内で例外になり、**画面が止まる**ことがあった（M2からの既存不具合。滴が多い入口プレイで顕在化）。最大の4つを残し、残りを量で重み付けして1つにまとめる `capLobes` で上限内に収める（色・量・面積は保存）。加えて、描画の一歩で想定外の例外が起きてもループを止めず、1回だけ記録する保険を入れた。テスト追加。

## 個数ごとの描画時間

条件: MacのApple M1 GPU（ANGLE Metal）、ヘッドレスChrome、390×844・DPR2、画面同期の上限なし、1滴をその場で小さく揺らし続け個数を保つ。5秒のウォームアップ後9秒。スマホ実機の値ではない。`artifacts/m3/drop-count-benchmark.json`

| 個数 | 高画質 中央値 / p95 (ms) | 軽さ優先 中央値 / p95 (ms) |
|---:|---|---|
| 12 | 2.6 / 5.1 | 1.7 / 3.9 |
| 24 | 3.8 / 7.2 | 2.1 / 2.7 |
| 36 | 4.2 / 7.6 | 2.6 / 3.2 |
| 48 | 5.2 / 7.5 | 3.2 / 3.8 |
| 60 | 5.8 / 8.0 | 3.9 / 4.6 |

個数にほぼ比例して増えるが、60個でも1コマ16.7 msに対して余裕がある。スマホGPUはこれより数倍遅い可能性があり、60個・高画質の実機確認はM4で必要。

## 10分の連続操作

GPU描画のヘッドレスChrome、390×844、12個。無作為に投げる245・押し込み108・2回タップ93・一時停止32・待機20、90秒ごとに「もう一度」6回。30秒ごとに記録。`artifacts/m3/ten-minute-soak.json`

- 例外・警告0、掴みっぱなし0、常に60 fps。
- 色の総量の誤差0（融合109回・分離27回を含む）。
- 描画資源は滴の数に合わせて増減し蓄積しない（テクスチャ4、プログラム9で一定）。JSヒープは39〜80 MBを上下し増加傾向なし。
