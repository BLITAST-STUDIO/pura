# M4の仕上げ確認 — 60個の長時間と、スマホ計測（2026-09-26）

## 60個・10分の連続操作

自由モード60個・三色・押し込み混色。GPU描画のヘッドレスChrome（Apple M1、390×844）。無作為に投げる219・押し込み93・2回タップ93・盤面をなぞってまとめる56、並べ直し17回（60秒ごと／6個未満で）。融合1,007回・分離14回。`artifacts/m4/sixty-drop-ten-minute-soak.json`

- 例外・警告0、掴みっぱなし0、色の総量の誤差0。
- 描画資源は滴の数に合わせて増減し蓄積なし（テクスチャ4・プログラム9で一定）。JSヒープ39〜118 MBで増加傾向なし。
- ただし大量の融合が重なる瞬間にコマ間隔が33〜67 msに伸びる引っかかりを確認 → 下記で改善。

## 連続融合の引っかかりの改善

60個1色を盤面ごとなぞってまとめる操作（画面同期なしで実コストを計測、3回平均）:

| | 改善前 | 改善後 |
|---|---:|---:|
| コマ間隔の中央値 | 約13 ms | 約8 ms |
| p95 | 約33 ms | 22〜25 ms |
| 最大 | 120〜170 ms | 約34 ms |
| 33 ms超 | 13〜25回 | 1〜3回 |

CPUプロファイルで原因を特定して順に対処（見た目は公開版と画素差0を3画面で確認）:

1. 融合途中の表面計算（マーチングキューブ）: 距離計算を `Math.hypot` から平方根へ、滑らかな結合の平坦な場合を省略。小さな雫は格子を粗く（半径50以上40³、30以上32³、それ未満24³）。格子を使い回すプール。1コマの表面更新を6個までに制限し、見送った雫は前回の形で描画と光路をそろえる。未構築の最初のコマは丸い雫で表示。
2. GPUへの転送: 表面の更新で確保済み最大18000三角形分を毎回送っていたのを、描画する分だけに（`addUpdateRange`）。外接球の毎フレーム全走査をやめ、既知の大きさから設定。
3. 大きな雫が小さな雫（結果の12%未満）を吸い込むときは融合途中の表面を作らない（形の差は見えず、なぞる操作の大半を占める）。同程度の大きさの融合（3面・入口プレイの承認済みの見た目）は従来どおり。
4. 床の影・光の模様・しぶき・床光の点のマテリアルはトーンマッピングの処理を含まないため `toneMapped: false` に。背景撮影と画面描画でプログラムが毎回切り替わるのを防ぐ（見た目は不変）。

残りは主にGPUの描画待ち（60個の透明な雫の屈折描画そのもの）。スマホ実機の数値を見て画質との兼ね合いを判断する。融合ごとのマテリアル新規作成（約1割）は未対処。
