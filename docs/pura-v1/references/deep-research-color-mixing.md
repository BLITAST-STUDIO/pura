# PURA FLOW ― 「融合する色」を本物らしく、しかも美しく見せるための設計研究

## 結論：PURA FLOWでは「色を混ぜる」のではなく「色素の量を保存し、光の吸収を混ぜる」

添付画像の現在のPURA FLOWは、すでにかなり良い地点にいます。CYAN、ROSE、AMBERの雫は、単なる不透明な色玉ではなく、**透明な物体の内部に色が存在している**ように見え始めています。

ここから「本当に色の付いた水滴・液体・ゼリーが融合している」と感じるところまで持っていくために、最も重要な考え方は一つです。

> **RGBの色を平均するのではなく、各雫が持っている“色素の量”を保存し、その結果として光がどれだけ吸収されるかを描画する。**

透明な着色液体では、見えている色は物体表面に貼られた色ではありません。光が液体内部を通る間に特定の波長が吸収され、残った光が目に届くことで色が生じます。Beer–Lambert型の吸収では、光路長と吸収係数に応じて透過光が指数的に減衰します。Khronosの`KHR_materials_volume`も、この考え方を `T(x)=exp(-σx)` として採用し、`attenuationColor`と`attenuationDistance`から吸収係数を定義しています。citeturn10search2turn5view5

つまりPURA FLOWにとって、

**雫の色 ≠ 固定RGB**

です。

より正確には、

> **照明 × 背景 × 表面反射 × 屈折 × 液体内部の厚み × 各色素の吸収量**

の結果として、その瞬間の色が決まります。KhronosのVolume仕様でも、表面のBase Colorと内部のAbsorptionは別物として扱われ、吸収の場合は物体が厚い部分ほど色が深くなります。citeturn10search2turn10search4

これはPURA FLOWにとって非常に都合がいい性質です。

**大きな雫ほど中央の色が深くなり、薄い縁は透明になる。**

同色を何個も融合して大きな一滴へ育てること自体が、そのまま視覚的な報酬になるからです。

私なら、PURA FLOWの色システムを次の三層に分けます。

| 層 | 管理するもの | 役割 |
|---|---|---|
| ゲーム状態 | 体積とCYAN/ROSE/AMBERの色素量 | 正しい混合比を永久に保持する |
| 混合状態 | 色素が雫内部のどこに存在するか | 融合直後の二色・渦・筋を表現する |
| レンダリング | 吸収・厚み・屈折・表面反射 | 最終的にユーザーが見る色を決める |

**この三つを分離することが、最重要です。**

## 色の割合は「画面上の大きさ」ではなく、体積で保存する

RYOさんが挙げた、

> 同じサイズなら半々。  
> その倍の大きさになったものに、元と同じサイズを追加したら2/3対1/3。

これはそのまま実装できます。

各雫に、

\[
V=\text{液体の体積}
\]

と、

\[
\mathbf q=(q_C,q_R,q_A)
\]

を持たせます。

`qC`、`qR`、`qA`はそれぞれCYAN、ROSE、AMBERの**色素量**です。

二つの雫が融合したら、

\[
V_{new}=V_1+V_2
\]

\[
\mathbf q_{new}=\mathbf q_1+\mathbf q_2
\]

とするだけです。

最終的な各色素の濃度は、

\[
\mathbf c_{new}=
\frac{\mathbf q_{new}}{V_{new}}
\]

になります。

この「量を足し、全体量で割る」という構造をゲーム状態の真実にしておけば、融合回数が増えても比率が壊れません。

### RYOさんの例をそのまま計算すると

最初のCYAN一滴を体積`1`とします。

```text
CYAN
体積 = 1
色素 = C:1 R:0 A:0
```

同じ大きさのROSEを融合。

```text
CYAN 1 + ROSE 1
↓
体積 = 2
C:1 R:1 A:0
```

したがって、

```text
CYAN 50%
ROSE 50%
```

です。

さらに、最初と同じサイズ`1`のAMBERを融合。

```text
現在 2 + AMBER 1
↓
全体 = 3
```

「現在の液体」と「新しいAMBER」の比なら、

```text
2/3 : 1/3
```

です。

ただし、現在の液体がCYANとROSEの半々だったため、最終的な色素内訳は、

```text
CYAN  1/3
ROSE  1/3
AMBER 1/3
```

になります。

逆に最初の2滴が両方CYANだったなら、

```text
CYAN 2/3
AMBER 1/3
```

です。

ここで非常に重要なのは、**画面上の半径をそのまま混合比に使わないこと**です。三次元の球では体積は半径の三乗に比例するため、見た目の半径と液体量は同じ尺度ではありません。実際のPURA FLOWでは完全な球ではなく盤面上の液滴形状なので、ゲーム内部で持つ`volume`または既存の`mass`を色素保存の基準とし、描画サイズから逆算しない方が安全です。

### 同色同士を混ぜたときも重要

CYAN 100%の同じ大きさの雫を二つ融合すると、

```text
体積 1 + 1 = 2
色素量 1 + 1 = 2
濃度 2 / 2 = 1
```

なので、**CYANの濃度自体は変わりません。**

それでも大きくなった雫は、中央が以前より深いCYANに見えて構いません。

その理由は「濃度が上がったから」ではなく、

**光が液体内部を通る距離が長くなったから**

です。

KhronosのVolume仕様では、吸収係数を`σ`、液体内を通る距離を`x`とすると、

\[
T(x)=e^{-\sigma x}
\]

となり、同じ材質でも厚いところほど透過量が減ります。公式のAttenuation Testも、同じ着色材質で厚い物体ほど深い色になることを検証しています。citeturn10search2turn10search4

**これはPURA FLOWで絶対に取り入れたい表現です。**

## CYAN・ROSE・AMBERはRGB平均ではなく「吸収」で混ぜる

現在の三色構成は、実は非常に相性がいいです。

透明液体を「透過する光」として考えるなら、概念的には、

**CYAN系色素**  
→ 赤側を多く吸収し、青緑側を残す。

**ROSE/MAGENTA系色素**  
→ 緑側を多く吸収し、赤・青側を残す。

**AMBER/YELLOW系色素**  
→ 青側を多く吸収し、赤・緑側を残す。

という**減法的な挙動**として設計できます。

複数の吸収成分が存在する場合、各成分の吸収寄与を足し合わせて透過量を計算するのがBeer–Lambert型モデルの自然な拡張です。citeturn2search1turn5view5

### ゲーム用に簡略化するなら

各基本色に、RGBそれぞれをどれだけ吸収するかを表す値を持たせます。

例えば概念的には、

```text
CYAN absorption  = 赤を強く、緑を少し、青を少し吸収
ROSE absorption  = 緑を強く、赤と青を少し吸収
AMBER absorption = 青を強く、赤と緑を少し吸収
```

です。

各雫の混合状態から、

\[
\sigma_{mix}
=
c_C\sigma_C+
c_R\sigma_R+
c_A\sigma_A
\]

を計算し、そのピクセルを通る液体の厚み`L`に対して、

\[
T_{RGB}
=
e^{-\sigma_{mix}L}
\]

を計算します。

これだけでも、

**「色付き透明体の内部で色が混ざっている」**

という印象は、単純なRGB平均より大幅に向上します。光学的な体積吸収を扱うglTF Volumeも同じ指数減衰型のモデルを採用しています。citeturn10search2

### なぜ普通のRGB平均が良くないのか

例えば、

```text
mixedColor = (colorA + colorB) / 2
```

をsRGB値に直接行う方法は、まず光の計算としても線形ではありません。sRGBなど一般的な表示RGBは伝達曲線によって符号化されているため、物理量として演算するなら線形光へ戻す必要があります。W3Cの色仕様でも、線形RGBと符号化RGBは区別されています。citeturn2search2

さらに、線形RGBへ変換して平均したとしても、それは**透明な色素溶液が吸収によって混ざるモデルにはなりません。**

したがって優先順位は、

| 方法 | PURA FLOW適性 |
|---|---:|
| sRGBを直接平均 | × |
| Linear RGBを平均 | △ |
| HSV/HSL/OKLCHで補間 | △ アート用 |
| 色素量＋RGB吸収係数 | **◎** |
| 色素量＋スペクトル吸収 | **究極候補** |

です。

### 本気で「究極」を狙うならスペクトル方式

RGBではなく、例えば可視光を複数波長に分けて、

\[
\sigma(\lambda)
\]

を各色素に持たせます。

すると、

\[
\sigma_{mix}(\lambda)
=
c_C\sigma_C(\lambda)+
c_R\sigma_R(\lambda)+
c_A\sigma_A(\lambda)
\]

となり、

\[
T(\lambda,L)
=
e^{-\sigma_{mix}(\lambda)L}
\]

で波長ごとの透過量を求められます。

最終的なスペクトルをCIEの標準等色関数でXYZへ変換し、ディスプレイRGBへ落とします。CIEは1 nm刻みの1931標準等色関数データも公開しています。citeturn4search1turn4search4

これはPURA FLOWに意外と大きなメリットがあります。

現在の画面にはすでに、

**「スタジオ」  
「自然光」**

という照明切り替えがあります。

RGBだけで作った色では、「どんな照明でも同じような色」に寄りやすい。一方、現実の物質では照明のスペクトルが変わると見え方も変わります。同じ三刺激値に見える異なるスペクトルが照明変更によって一致しなくなる現象は、CIEがメタメリズムとして定義しています。citeturn4search0

したがって将来的には、

**スタジオライトでは深いローズ。  
自然光では少し透明感のある赤紫。**

といった繊細な変化まで作れます。

ただしリアルタイムで全ピクセルに何十波長もの計算を行う必要はありません。

私なら、

> **スペクトル計算を事前に行い、CYAN/ROSE/AMBERの比率から結果を引けるLUTを生成する**

方式をまず試します。

これなら、物理的な色混合の傾向を残しながら実行時負荷を抑えられます。

## 本物らしさを一段上げるのは「混ざった最終色」より「混ざっていく途中」

ここは今回の調査で、PURA FLOWに非常に重要だと感じた部分です。

現実の二つの着色液滴は、

**接触した瞬間に全体が一色になるわけではありません。**

接触するとまず液体同士をつなぐ細いブリッジ、いわゆるneckが形成され、表面張力によって急速に広がります。液滴合体は表面張力・慣性・粘性の競合で進むことが、液滴合体研究で詳しく調べられています。citeturn0search5turn0academia29

さらに重要なのが**内部の色**です。

2026年のPhysical Review Fluids研究では、固体面上で衝突・合体する液滴を移流拡散方程式とVOF法で調べたところ、衝突と形状緩和の短い時間には完全な混合は起こらず、均質化はより長い時間尺度の分子拡散に大きく依存する条件が示されています。citeturn5view2

過去の実験でも、近い大きさの液滴では合体直後にほとんど混ざらないケースがあり、大きさの差があると内部の渦輪などによって混合が促進されることが報告されています。citeturn3search7turn3academia40

これはゲームとして非常に使えます。

### 悪い融合

```text
CYAN  ●  → ←  ● ROSE

接触

紫 ●
```

一瞬で紫。

ゲームの情報としては正しいですが、物質感がありません。

### PURA FLOWで狙いたい融合

```text
CYAN       ROSE
  ●         ●

      ↓

  ◯━━◯
   細いneck

      ↓

   ◉◉
二色がまだ左右に残る

      ↓

  ～～～～
内部で色の筋が引き伸ばされる

      ↓

    ●
深い混色へ収束
```

この**0コンマ数秒から数秒の過程**が、PURA FLOWでは最高のVFXになります。

厳密な現実では完全混合がかなり遅い場合もあるため、ゲームでは時間を圧縮して構いません。重要なのは、

> **即時RGB変更にしない**

ことです。

たとえばPURA FLOW向けの初期チューニング案として、

```text
0–80 ms      接触・neck生成
80–250 ms    二つの色塊が押し込まれる
250–700 ms   色の筋・渦が内部を走る
700–1500 ms  最終色へなじむ
```

くらいから試す価値があります。

これは物理定数ではなく、**PURA FLOWの快感を狙うアートディレクション用の初期値**です。

速く激しくぶつけた場合は混ざりが速く、静かに接触した場合は二色の領域が少し長く残る、という演出も説得力があります。実際の液滴研究でも、衝突条件、液滴サイズ比、基板濡れ性、内部流れなどによって混合挙動は変化します。citeturn3search0turn5view2

### 最もPURA FLOWらしいアイデア

**混色速度を衝突エネルギーに連動させる。**

ゆっくり融合：

> 二つの色がゆっくり溶け合う。

高速で滑走して衝突：

> 色が内部へ勢いよく巻き込まれ、渦状の筋が生まれ、一気になじむ。

こうすると、

**操作 → 物理 → 見た目**

がつながります。

プレイヤーは説明されなくても、

> 「強く当てると、中までグワッと混ざる」

と身体的に理解できます。

これはPURA FLOWが目指している**「説明ではなく発見」**とも非常に相性がいいです。

## Three.jsで実装するなら「材質色」ではなく「体積吸収」を中心にする

現在のPURA FLOWの方向なら、Three.js側にもかなり使える土台があります。

現在の`MeshPhysicalMaterial`には、Transmission、IOR、Thicknessなど透明体向けの物理パラメータがあります。Transmissionを使う場合も、透明度を単純なopacityとして扱うのではなく、透過する誘電体として扱える設計です。citeturn7search0

さらに現行Three.jsの`MeshPhysicalNodeMaterial`には、

`attenuationColorNode`  
`attenuationDistanceNode`  
`iorNode`  
`thicknessNode`  
`transmissionNode`

が用意され、Node側から物理材質のこれらの値を上書きできます。したがって、PURA FLOW固有の色素量から算出した吸収を動的に材質へ流し込む設計とも相性があります。citeturn11search1

### 私なら内部データをこうします

```ts
type DropletComposition = {
  volume: number;

  dyeAmount: {
    cyan: number;
    rose: number;
    amber: number;
  };
};
```

融合は極端に単純です。

```ts
merged.volume = a.volume + b.volume;

merged.dyeAmount.cyan =
  a.dyeAmount.cyan + b.dyeAmount.cyan;

merged.dyeAmount.rose =
  a.dyeAmount.rose + b.dyeAmount.rose;

merged.dyeAmount.amber =
  a.dyeAmount.amber + b.dyeAmount.amber;
```

ここには**RGBを一切入れません。**

そしてレンダラー側で、

```text
dye amounts
↓
concentration
↓
absorption coefficients
↓
attenuation
↓
rendered RGB
```

へ変換します。

これが強いです。

あとからCYANの見た目を変更しても、ゲーム中の純度データや過去の融合結果を壊しません。

### 空間的な混ざりも別に持つ

さらに上を狙うなら、雫内部に小さな2D濃度テクスチャを持たせます。

例えば64×64程度の領域に、

```text
R channel = cyan concentration
G channel = rose concentration
B channel = amber concentration
```

を保存する。

融合直後は、

```text
左半分 CYAN
右半分 ROSE
```

のように配置。

そこへ簡易的な内部速度場を与え、

**advection（流れによる移動）  
＋ diffusion（拡散）**

を行います。

液滴混合研究でも色素濃度は移流拡散方程式でモデル化されており、2026年のAPS研究もVOFとadvection-diffusionを組み合わせています。citeturn5view2

CG側でも、速度場に密度や色素を移流させる方法は長年リアルタイム流体表現に利用されており、StamのStable Fluidsはその代表的な基礎研究です。citeturn8search0

ただしPURA FLOWでは、完全なNavier–Stokesシミュレーターにする必要はありません。

固定俯瞰カメラで、薄い液滴を主に上から見るのであれば、

> **見た目用の2D色素場だけ流体的に動かし、外形の物理は現在のゲーム用モデルに任せる**

というかなり賢い近似ができます。

これは試す価値が高いです。

## 究極のリアリティを確認するための開発チェックリスト

以下は、私ならPURA FLOW開発チームが**一滴→融合→連鎖融合**を評価するときに使うチェック項目です。

単なる「綺麗かどうか」ではなく、ひとつずつ潰せる形にしています。

### 色と光

| 確認項目 | 合格の目安 |
|---|---|
| **厚みによって色が変わるか** | 縁は明るく透明、中央は深くなる。Volume吸収では光路長によって透過量が変わる。citeturn10search2turn10search4 |
| **大きな同色雫が不自然に別色にならないか** | 濃度は同じまま。中央だけ光路長により深く見える |
| **表面ハイライトと内部色が分離しているか** | 色付きプラスチックのベタ塗りではなく、表面反射と透過色を別に感じる。誘電体表面の反射・透過はFresnel挙動に支配される。citeturn12search0 |
| **背景が雫越しに変形するか** | 透明度ではなく屈折として見える。Volumeは厚みを持つ屈折・吸収を扱う。citeturn5view4 |
| **雫が厚いほど背景色が色素の影響を受けるか** | 中央を通した背景ほど着色する |
| **CYAN＋ROSEなどが単純RGB中間色になっていないか** | 透過色素らしい減法的な結果になる |
| **照明変更で色の感じ方が少し変わるか** | Studio/Natural Lightの違いが物質に反映される。スペクトルが異なれば色刺激も変化し得る。citeturn4search0turn4search4 |
| **白いハイライトが色素色で塗りつぶされていないか** | 「表面に光が映る」感覚を保つ |

### 混合比

| 確認項目 | 合格の目安 |
|---|---|
| **1:1が本当に1:1か** | 同体積なら色素量50:50 |
| **2:1が2:1として保存されるか** | 既存2体積＋新規1体積なら2/3:1/3 |
| **10:1でも小さい方の影響が適切か** | 小滴が巨大滴全体を突然別色にしない |
| **順番を変えても最終色が同じか** | A+B+CとC+B+Aの最終組成が一致する |
| **融合を100回繰り返しても色が漂流しないか** | 表示色ではなく色素量を高精度で保持する |
| **一度混ざった雫をさらに混ぜても情報が失われないか** | 前回のRGB結果を次の入力色として使わない |
| **分離後も色素量が保存されるか** | 分離前後の総量が一致する |
| **見た目の半径を混色重量に使っていないか** | `mass`/`volume`を基準にする |

### 融合の瞬間

| 確認項目 | 合格の目安 |
|---|---|
| **接触点にneckが生まれるか** | 二球の瞬間切替ではなく、細い接続が広がる。液滴合体はbridge/neck形成から進む。citeturn0academia29 |
| **融合時に一度形が伸びるか** | 衝突軸に応じた一時的変形 |
| **融合後に振動するか** | 一度膨張・収縮して減衰 |
| **体積が保存されて見えるか** | 合体後に液体量が減った・増えた印象を与えない |
| **色境界が一瞬残るか** | 接触直後から均一色にしない |
| **内部色が接触軸に沿って流れるか** | ランダムノイズではなく衝突方向との因果がある |
| **大小の融合で流れが非対称になるか** | 小さい雫の色が大きい側へ巻き込まれる印象。サイズ比は内部流動に影響し得る。citeturn3academia40 |
| **高速衝突と低速接触で混ざり方が違うか** | 衝突エネルギーが高いほど強い内部流動を演出する |
| **融合途中でも次の雫を吸収できるか** | 演出待ちでゲームプレイを停止しない |

### 色が混ざる途中

| 確認項目 | 合格の目安 |
|---|---|
| **二色が領域として存在する瞬間があるか** | 最終色へ即座に切り替わらない |
| **境界が単純なクロスフェードではないか** | 流れに沿って引き伸ばされる |
| **細い色の筋が生まれるか** | 液体内部を色素が移流しているように見える |
| **筋が永久に残らないか** | 最終的には拡散して均質化する |
| **混色時間がサイズに応じて変わるか** | 巨大滴と微小滴で同じ秒数に固定しない |
| **移動中も内部色が少し遅れて動くか** | 液体に慣性があるように感じる |
| **急停止後も内部の色が少し動くか** | 外形が止まった瞬間に内部まで完全停止しない |
| **毎回同じ模様になりすぎないか** | 衝突角度・速度・サイズから変化を作る |

### 「綺麗さ」を守る確認

ここは物理よりPURA FLOWにとって重要です。

| 確認項目 | 判断 |
|---|---|
| **現実通りにした結果、色が汚くなっていないか** | 必要なら吸収スペクトルをアートディレクトする |
| **三色混合がすぐ黒・茶色になりすぎないか** | 物理値を少し調整して透明感を残す |
| **小さい雫も色を識別できるか** | 薄い領域でもCYAN/ROSE/AMBERが読める |
| **背景によって色が消えないか** | 盤面と照明も材質設計の一部として調整 |
| **Bloomで綺麗に見せているだけになっていないか** | Bloomを切っても物質感が成立する |
| **静止画だけ綺麗になっていないか** | 滑走・衝突・融合途中・停止後すべて確認 |
| **色の変化がゲーム情報を壊していないか** | 純度や主色が視覚的に判別できる |
| **美しさと物理性の優先順位が明確か** | PURAでは“説得力のある美しさ”を最優先 |

## PURA FLOW向けの実装優先順位

この研究をそのままCodexへ落とすなら、私は一度に全部やらせません。

まず**現在の一滴の材質**を使って、次の比較実験を作るのが最も効率的です。

### 最初の実験

同じ形のCYANの雫を、

```text
A : 現在の実装
B : RGBで色を設定
C : Volume absorptionで色を生成
```

の三つ並べます。

大きさも、

```text
Small
Medium
Large
```

を用意します。

合格条件は、

> **Cだけが、「同じ色の液体なのに厚いところほど自然に深い」と感じられるか。**

Khronos自身も、厚み・attenuationColor・attenuationDistanceの組み合わせを検証する専用サンプルを公開しています。PURA FLOWでも同様のMaterial Testを持つ価値があります。citeturn10search4

### 次の実験

CYANとROSEを、

```text
1 : 1
2 : 1
4 : 1
1 : 2
1 : 4
```

で混ぜます。

そして、

**sRGB平均  
Linear RGB平均  
Absorption Mix**

を横に並べる。

これだけで、PURA FLOWにどの色モデルが合うかかなり明確になります。

### その次に「混ざる途中」を作る

最初は本格流体でなくて構いません。

```text
merge開始
↓
二つの色領域を保持
↓
衝突軸方向へ引き伸ばす
↓
簡易渦でwarp
↓
時間とともにdiffusion
↓
最終的な均一組成へ収束
```

です。

ここまでできれば、例えばCYANの大きな雫が滑り、

**小さなROSEへ衝突  
→ ROSEが内部へ入り込む  
→ 紫青の筋がぐるりと回る  
→ 大きな一滴として滑走を続ける  
→ 内部の色だけ少し遅れて落ち着く**

という、かなり強烈な映像になります。

しかもこれは単なるVFXではありません。

**「自分がぶつけた」という操作結果が、液体内部へ痕跡として残る。**

PURA FLOWが目指す「触感のあるUX」にとって、かなり重要な要素になると思います。

最終的には、私は現実を100%コピーする必要はないと考えます。

守るべき物理は、

**色素量が保存される。  
大きさに応じて比率が変わる。  
厚みによって色が深くなる。  
透明体として背景を透過・屈折する。  
融合しても瞬間的には完全均一にならない。  
衝突の方向と勢いが内部の動きに影響する。**

ここです。これらは光学・流体力学の根拠を持たせられます。citeturn10search2turn5view2turn3search0

一方で、

**色素の吸収スペクトル、  
混色後の最低明度、  
混ざるまでの時間、  
内部渦の強さ、  
コースティクスの明るさ、  
「ぷるん」の誇張量**

は、PURA FLOWのために美しく調整していい。

その境界が非常に重要です。

> **物理法則をゲームに従わせるのではなく、物理法則を“説得力を生む骨格”として使い、その上で最高に美しく気持ちいい液体を作る。**

添付画像の現在地点から次に大きく効くのは、解像度やエフェクトの追加よりも、**「色が表面に付いている」のではなく「色が雫の中に溶けている」状態を成立させること**です。

そこまで到達すると、CYAN一滴を眺めているだけでも綺麗なのに、ROSEへ衝突した瞬間、二つの色が内部で巻き込まれながら一つになる。

その現象自体が、**PURA FLOWを延々触ってしまう報酬**になり得ます。
