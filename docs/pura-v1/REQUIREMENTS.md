## 1. プロダクトの目的

### 1.1 定義【合意事項】

PURAは**ゲームとデジタルトイの中間にある、触れる物質体験**。第一印象でパズルの理解や上達を要求せず、「綺麗」「動かしたい」から参加できるものにする。[U1][S1]

体験の流れは次の通り。

**触りたくなる → 触る → 動く → くっつく → 気持ちいい → もう一度試す → 自分で工夫を発見する。**

内部には純度・質量・進路選択のゲーム性を残すが、それを入口の負担にしない。「非ゲーマー向け」を主要な売り文句にせず、誰でも触りたくなる広い入口を目指す。これは市場成果の証明ではなく、設計方針である。

### 1.2 最も重要な一場面【合意事項】

一滴を弾く。滑る。道中の同色の雫を二つ、三つと吸収する。接触部がつながり、輪郭と光が変化し、色が厚くなり、最後は一つの雫として穏やかに止まる。その途中も直後も、再びつかめる。

**この数秒間をPURAの看板体験とする。** メニュー、ステージ数、新機能より先に完成度を上げる。

### 1.3 品質判断の原則

操作の連続性・分かりやすさと、動的な美しさを**両方の合格条件**にする。軽いが平凡な円、綺麗だが触れない映像は、どちらも不合格。両立が難しい場合は個数・解像度・周辺演出から範囲を絞り、入力や融合を犠牲にしない。

「リアル」は、水滴らしい光と形の説得力を指す。実物の水の完全再現、全光路の追跡、科学的に厳密な流体シミュレーションを必須条件にしない。異色が通常は反発することは、ゲーム固有の物質法則として認める。

## 4. 継承するゲームルール

### 4.1 基本ルール【継承仕様】

| ID | 要件 | 根拠・注意 |
|---|---|---|
| G-01 | 色はシアン・ローズ・アンバーの3系統 | 材質の色調整と、論理上の色IDを分離する |
| G-02 | ドラッグしてつかみ、離すと現在の速度を受け継いで滑る | 弾く操作に別の必須ボタンを追加しない |
| G-03 | 同色の雫は接触等の既存条件で融合する | 実装上の同色は主成分色の一致 |
| G-04 | 融合中も入力と次の吸収を受け付ける | 見た目のアニメーション完了待ちを入れない |
| G-05 | 異色の通常接触は反発する | 接触しただけで全色を混ぜない |
| G-06 | 掴みを伴う一定の押し込み・低相対速度条件で異色が混ざる | 細かい判定は基準 `sim.ts` を継承 |
| G-07 | 色成分から純度を算出する | 下記4.2。照明の見た目から判定しない |
| G-08 | ダブルタップ／ダブルクリックで条件付き分離 | 混入した一定量以上の非主成分を取り出す。自由二分割ではない |
| G-09 | ゲームオーバー・強制時間切れを設けない | 混色は取り返せる状態。リセット手段を残す |
| G-10 | 壁反射・減衰・既存の弱い引力／反発を比較基準に残す | 本文4.3参照。無断で「純粋な物理」に置換しない |
| G-11 | ステージでは質量と純度の条件で色ごとの核を判定する | 本文4.4参照 |
| G-12 | サンドボックスはクリア目標なし | エンドレスは「自動補充し続ける」の意味ではない |

出典: `sim.ts`、`palette.ts`、`levels.ts`。[B2][B3][B4]

古いS/M/L方式、異色衝突で必ず破裂する方式、最大サイズは融合できない方式を混在させない。今回ユーザーが提示した概要と基準ソースは、質量・純度・条件付き混色を持つ版である。[U1][B2]

### 4.2 質量・色・純度【継承仕様】

各雫は三色それぞれの非負の成分量を持つ。

```text
mass = cyan + rose + amber
purity = max(cyan, rose, amber) / mass
mergedPigment = pigmentA + pigmentB
mergedVelocity = (massA * velocityA + massB * velocityB) / (massA + massB)
```

主成分色の同率時の優先順、微小質量の扱いも `palette.ts` を継承する。比較テストでは0除算を避ける。「同色を足せば必ず純度が上がる」ではなく、加えた成分に応じて計算する。例えば高純度の主成分色を足すと回復し得る。

現行の半径則は基本的に `mass = r²`、`r = sqrt(mass)`。描画を3Dにするという理由だけで立方根へ変更しない。融合演算の速度継承を守り、滑走を気持ちよくするための自動加速を密かに加えない。[B2][B3]

### 4.3 既存の力と、未採用アイデアの区別

基準ソースには、掴んだ雫の周囲で同色を弱く引き寄せ、異色を弱く遠ざける処理と、接近する同色の補助的な引力がある。これは継承対象。[B2]

`PURAの強み.txt` の「小さい雫を巻き込むと加速」「特定の組み合わせで一瞬だけ磁力」は、発見型デザインの例であって採用済み仕様ではない。新しいブースト、磁力コンボ、サイズ依存の摩擦や操作慣性を追加しない。導入するときは個別の仕様変更と比較検証を行う。[S1]

### 4.4 ステージ判定【継承仕様】

各色について、開始時に存在したその色の総成分量へ `targetFrac` を掛けて目標質量を作る。主成分色がその色で、必要純度以上の雫から最大**総質量**のものを評価し、目標以上か確認する。全色の条件達成でクリアする。対象色の成分量そのものを核の達成質量として比較する別実装へ、無断で読み替えない。[B2]

| ステージ | 色数 | 初期個数 | 目標割合 | 必要純度 | 特記事項 |
|---|---:|---:|---:|---:|---|
| 1 覚醒 | 1 | 14 | 0.82 | 0.99 | シアン |
| 2 対 | 2 | 20 | 0.78 | 0.92 | シアン・ローズ |
| 3 三色 | 3 | 24 | 0.74 | 0.90 | 三色 |
| 4 密集 | 3 | 36 | 0.72 | 0.90 | 三色 |
| 5 臨界 | 3 | 24 | 0.78 | 0.97 | 三色 |
| 6 潮流 | 3 | 30 | 0.72 | 0.90 | 場の流れあり |
| 7 霧雨 | 3 | 48 | 0.70 | 0.88 | 小さな雫 |
| 8 核 | 3 | 42 | 0.76 | 0.94 | 三色 |

上表は基準 `levels.ts` の値。リメイク版の新しい難易度案ではない。星は達成核の平均純度を基準に、0.995以上で3、そうでなくステージ必要純度+0.04以上で2、それ以外で1という現行判定を継承する。[B2][B4]

ステージ7の「勢いよくぶつけると弾く」というヒントと、同色を高速でも吸収するコードには表現上の差がある。高速度の同色反発を追加せず、M4で操作説明を実挙動に合わせて確認・修正する。

### 4.5 サンドボックス【継承仕様】

初期数12〜60個、6個単位、現行既定値60を残す。小規模の質感試作が12個であることと、完成版の最大数を12個へ変更することを混同しない。自動補充は追加しない。M4では最大数と分離後の状態を検証する。[B4]

## 5. 操作要件

| ID | 操作 | 必須挙動 |
|---|---|---|
| I-01 | 掴む | 指・マウスの位置と対象が合う。小さい雫には周囲の選択余裕を持たせる。近接時は一貫した選択規則 |
| I-02 | 引く | 指への反応を先に返し、胴体の柔らかさを後から追従させる。ゼリー表現のために入力を遅らせない |
| I-03 | 弾く・離す | ドラッグから自然に滑走へ移行する。既存の速度と新しい投射速度を二重加算しない |
| I-04 | 融合中に再操作 | 新しい雫IDへ制御を継続する。掴み直しを強制しない |
| I-05 | 条件付き分離 | 誤ダブルタップとドラッグの競合を検証する。使い方は任意ヘルプでも分かる |
| I-06 | キャンセル | pointercancel・画面外リリース・フォーカス離脱で掴みっぱなしにしない |
| I-07 | 複数タッチ | 初期は1本での操作。2本目で勝手に対象を奪わない |
| I-08 | 一時停止・リセット | Esc/Rの既存操作を保ち、タッチでも同等操作に到達できる |
| I-09 | リサイズ・復帰 | 意図しない盤面消去や巨大な時間進行を防ぎ、座標変換を保つ |

入力の検査は、投影された水滴と盤面座標の対応を含む。見た目の膨らみだけ大きくして、触れているのに掴めない状態を避ける。設定UIやヘルプのクリックを盤面へ貫通させない。

## 6. ビジュアル・物質感

### 6.1 水滴の方向【合意事項】

ガラス玉、ゴム球、食品のゼリー、粘着性の強いスライムではなく、**水滴に少しだけ形を保つ性質を与えた、不思議な液体**を狙う。カラフルでも落ち着きがあり、触りたくなる透明感を持つ。[U1]

| ID | 要件 | 評価場面 |
|---|---|---|
| V-01 | 表面反射と透過が同時に読める | 静止とドラッグ。半透明の円や不透明な光沢球で代用しない |
| V-02 | 雫越しに盤面が形・厚みに応じて歪む | 模様入りの検査盤面で移動・変形を確認 |
| V-03 | 薄い縁と厚い胴体の色の深さに差がある | 三色それぞれ、大小の雫 |
| V-04 | 光の映り込み・法線が変形へ追従する | 引く、壁へ当てる、融合する |
| V-05 | 指と速度に反応する短い変形 | 長く弾み続けず穏やかに収束。収束時間は調整値 |
| V-06 | 融合時に接触部から連続した表面へ変わる | 2個→1個、融合途中の追加吸収 |
| V-07 | 接地感があり、盤面上に存在する | 高さ・影・反射の整合 |
| V-08 | 全ての操作対象と三色が見分けられる | 混色、密集、低品質設定でも検査 |
| V-09 | 近接しただけの異色が見た目上で融合しない | 弱い接触・強い衝突・混色成立の比較 |

厳密な屈折率の高さ自体を目的にしない。IOR・厚み・吸収・粗さは、**水らしさと読みやすさを作る調整パラメーター**として扱う。設定値だけで全光路の正確さを主張しない。

### 6.2 環境とカメラ【初期案】

暗いチャコール系の落ち着いた盤面、控えめな表面模様、柔らかく長い照明の映り込み。盤面にほぼ垂直〜軽く傾いた固定カメラ。操作は2D平面に限定し、プレイヤーにカメラ操作を要求しない。

参考画像は `references/visual-target.png`。**質感・光・色・空気感の目標**であり、プレイ画面の構図そのものではない。低い視点、強い被写界深度、ポスター文字、濡れた床全体、飛沫、虹、レンズ効果を全て再現する要件ではない。[S3]

プレイ中の強いボケ、画面揺れ、点滅、過剰なBloomは初期の既定にしない。水滴の輪郭・内部・融合を主役にする。床の集光模様は品質拡張候補であり、追加する場合は近似か実際の光計算かを記録する。

### 6.3 失格とする近道

背景に完成画像を置くだけ、透明な球を重ねて一方を消すだけ、輪郭は変わるがハイライトが固定、異色が常時メタボールでつながる、白飛び・暗さ・ボケで不具合を隠す、融合のたびに操作を止める。これらを完成扱いにしない。

M1の一滴には簡易形状を使えるが、M2の連続融合へつなげる境界を確保する。美しい一滴だけで融合方式まで成立したと判断しない。

## 7. 入口・画面・発見の設計

### 7.1 即触れる入口【合意方向＋初期案】

新しい通常入口は、必須のタイトル画面、START、ログイン、モード選択、チュートリアル完了を挟まず、読み込み後すぐに雫を操作できる。読み込み自体がゼロになるとは約束しない。[S1]

**実装中の旧版の入口はM4まで置換しない。** M1/M2は実験入口、M3は新版プレビュー。通常URLの切り替えは統合・承認後とする。

新入口は、既存サンドボックスと同じ基本法則を使う「入口プレイ」という薄い構成。別の大規模モードは作らない。初期案は三色合計12個の管理された配置。近い位置に同色を数個置き、最初のドラッグや軽い弾きで融合を発見しやすくする。既存サンドボックスの60個設定を勝手に書き換えない。

### 7.2 最初の30秒の設計例【初期案】

下表は観察上の目安であり、秒数による強制進行・操作ロック・要素アンロックを実装しない。

| 目安 | ユーザーが経験すること | システム側の設計 |
|---|---|---|
| 表示直後 | 綺麗な雫がある、触れそう | 盤面と水滴を優先表示。不要な文章や許可要求なし |
| 最初の接触 | 自分の指で動いた | 即座の入力反応と小さな形の変化 |
| 初回の融合 | くっついて大きくなった | 同色の自然な接近配置。明瞭な融合と穏やかな収束 |
| 次の操作 | 弾くと滑る、道中でさらにくっつく | 連鎖できる道筋はあるが、自動照準や自動成功は使わない |
| その先 | 角度や順番を試したい／ただ眺めたい | 操作継続。説明画面や採点で遮らない |

初回成功は配置によって助けるが、隠れた加速や強制磁力で演出しない。人が触る前に全て自動融合して体験を奪わない。

### 7.3 UIを少なくするが、使い方を消さない

| 場面 | 表示するもの／扱い |
|---|---|
| 通常の入口プレイ | 盤面と雫が主役。端に控えめな設定・ヘルプへの入口 |
| 初回に操作されないとき | 必要に応じて短い「なぞって、動かす」程度の補助。操作を遮らない。任意で消せる |
| 設定 | 音、動きを抑える、画質、並べ直し、パズル／サンドボックスへの入口 |
| パズル | 核の進捗・必要純度・選択中の純度を必要に応じて見られる。情報を完全に隠さない |
| 任意ヘルプ | ドラッグ、滑走、同色融合、異色混色、条件付き分離を短く説明 |

「説明より発見」は、気づけない人を置き去りにする指示ではない。ダブルタップ分離のように見つけにくい操作には任意の補助を残す。操作後の強制ポップアップ、常時スコアの大表示、ランキングの誘導は不要。

### 7.4 まとまった後のループ【初期案】

入口プレイでは採点・強制クリア画面・自動補充・自動遷移を行わない。まとまった雫をそのまま動かせる。必要になれば小さな「もう一度」で管理された初期盤面へ戻れる。

既存パズルのクリア条件と星は維持し、表示は体験を過度に遮らない方向へ調整する。次の面への遷移はユーザーの選択。既存サンドボックスのリセット・初期数変更は残す。入口プレイの「同じ配置へ戻す」と、既存モードの再生成を区別する。

## 9. 技術方針とアーキテクチャ

### 9.1 採用して着手する初期案

| 領域 | 初期案 | 決定理由・変更条件 |
|---|---|---|
| アプリ基盤 | 既存React + TypeScript + Vite | 全面移植せず資産と比較環境を残す |
| 新描画 | Three.jsを追加。初期比較はWebGL2 | 現行のThree.js導入を仮定しない。依存追加時に版を確認 |
| 物理 | `PuraSim` を再利用し、小さいアダプターを追加 | 滑走とルールを比較可能に保つ |
| 操作空間 | 2D平面 | 高さ方向の操作や自由カメラを追加しない |
| 見た目 | 3D、または3D相当の厚み・法線・屈折を持つ描画 | 手法名でなくV要件と性能で評価 |
| UI | 既存Reactの延長 | 毎フレーム全雫をReact stateへ流さない |
| 検証 | 既存ツールを優先し、不足する小さなテスト環境を追加 | 実際のスクリプトを確認してからコマンドを選ぶ |
| 配信 | 静的Web配信可能な構成 | 実行時AI APIやバックエンドを必須にしない |

現行 `package.json` にThree.jsはない。現行描画は独自WebGL。Three.jsの物理ベース材質は透過・IOR・厚み・吸収を扱えるが、設定だけで融合表面・実厚み・多重屈折を解決するわけではない。[B1][B5][T1]

WebGPU専用化、WebGL/WebGPUの二重実装、Unity/Unrealへの移植を初回に並行して行わない。方式変更はM1/M2の具体的な画質問題・性能結果に基づき判断し、記録する。

### 9.2 レイヤー境界

```text
Pointer入力 → 盤面座標変換 → PuraSim（位置・速度・色・質量・ルール）
                                      ↓ 読み取り専用フレーム＋イベント
                                 水滴の形状・変形・厚み
                                      ↓
                                 反射・屈折・影・描画

React UI ↔ モード・設定・進捗（必要な頻度だけ更新）
```

レンダラーはゲームの質量、成分量、衝突、勝敗を変更しない。映像用の変形・揺れ・補間は物理座標を上書きしない。色の見た目を調整しても論理成分は変えない。音や映像の完了通知を物理進行の条件にしない。

### 9.3 融合イベントと見た目の連続性

基準 `merge()` は2個から新IDの1個を作る。既存 `onMerge` は質量と混色フラグが中心で、融合前形状を再現する情報は不足する。[B2]

M2で小さい描画用イベントを追加する。必要情報はイベント順序／シミュレーション時刻、融合元IDと直前の位置・速度・半径・成分量、結果IDと結果状態。通知値は後から変わる参照ではなくスナップショットにする。既存音コールバックを壊さない。

A+B→C、直後にC+D→Eとなっても、途中の見た目を引き継ぎ、二重描画・古いIDへの入力・一瞬の消滅を防ぐ。同一描画フレーム内に複数イベントがあっても順序を保つ。物理更新単位での吸収頻度は既存と比較し、無限連鎖を同期的に計算する別ルールへ無断変更しない。

分離でも同様に必要なイベントを用意する。古い形を短時間残す場合、それは描画だけの状態であり、衝突・質量・雫数に参加させない。

### 9.4 表面生成の検証

M1は簡易な立体形状＋制御された変形＋透過材質を基準にできる。M2では局所的な連続表面を作る方式を検証する。メタボール、Marching Cubes、SDF／レイマーチング、画面空間の厚み場等は候補であり、採用済みの完成方式ではない。

材質、形状表現、表面抽出、描画は別の技術層。同列の「3方式」として無条件に3セット作らない。まず1案、問題があれば比較用の代替1案を、同じ盤面・照明・カメラ・入力条件で比較する。

盤面全体を高解像度3D格子にして毎フレーム再計算する構成を初手にしない。融合している局所群に計算を限定する。同色でも離れた雫を一つの形として無条件に接続しない。

### 9.5 光学表現の範囲

初期に優先するのは盤面の屈折、厚みによる色、表面反射、接地感。複数の透明体を経由する光、多重内部反射、厳密なコースティクスは後順位。透明物体の並び順、画面端、重なり、融合中の厚みを検証し、対応しない現象を正確に記録する。

質量則と見かけの体積を分ける。既存の半径を維持しながら高さをアート上の量として調整する初期案では、厳密な3D体積保存を主張しない。ただし融合直後に体積が唐突に跳ねる見え方は避ける。

### 9.6 新旧を比較できる実装

旧レンダラーを残し、新描画は独立ディレクトリと実験入口に置く。候補は `src/experiments/droplet-lab/` と `?lab=droplets`。これらは設計上の名前で、まだ作成済みではない。

物理・色・レベル・保存の全面リファクタリングを同時にしない。共通部分の変更が必要なら小さく切り出し、旧版と新版の双方へ回帰テストを行う。内部調整UIは公開版で隠す。

## 10. データ・保存・共有への備え

既存保存形式と保存キーをM0で確認し、初期実験から書き換えない。新設定は必要に応じて別バージョン／名前空間に置く。新入口の試遊で旧ステージのクリア記録を誤って更新しない。保存が使えない環境でも基本プレイを継続できることを目指す。

比較用の固定盤面は、論理盤面サイズ、雫ID、位置、速度、半径または質量、三色成分をデータとして固定する。乱数依存の処理は入力を制御できるようにする。seedだけで既存のMath.randomが決定論的になるとは扱わない。

将来の「動画と同じ盤面」には、配置IDだけでなくルール版・初期状態・盤面座標系の指定が必要になる。入口配置のデータをUIへ直接埋め込まず、取り出せる形にするところまでを初期の備えとする。共有サーバー、短縮URL、公開リンク生成、リプレイの完全再現は現スコープ外。

## 11. 性能・安定性の目標

### 11.1 数値の扱い

全て未実測の暫定目標。正式な対応機種・品質プリセットが決まって初めて合格範囲を宣言する。「全スマートフォンで60fps」「コンセプト画像と同じ画質で動作」とは約束しない。

| ID | 項目 | 初期目標／測定方針 |
|---|---|---|
| P-01 | 滑らかさ | 記録した基準PC・60Hz環境で60fpsを狙う。フレーム間隔中央値約16.7ms、p95 20ms以下を目安にする |
| P-02 | 連鎖中の安定性 | 平均FPSだけでなくp95と50ms超の間隔の回数を記録。静止だけの性能を合格にしない |
| P-03 | 入力応答 | 入力反映を不要なタイマー・アニメーション待ちで遅延させず、次の更新へ渡す。実入力遅延の測定値を捏造しない |
| P-04 | 初回の触り始め | 冷キャッシュ・20Mbps/RTT50ms相当の記録した条件で、ナビゲーション開始から操作可能まで3秒以内を暫定目標にする |
| P-05 | 連続操作 | M3で10分の実操作と、リセット／再入場を繰り返して固着・消失・リソース増加を確認 |
| P-06 | 実際の利用場面 | 動画再生と同時利用、モバイル継続操作を独立した測定条件として残す |

P-04は工学上の初期案で、実際の通信速度や端末の保証ではない。M1で必須にするのは計測方法と基準の記録まで。最終的な読み込み要件はM3/M4で判断する。低解像度でも操作できる状態を先に出し、重い素材待ちの演出を作らない。

### 11.2 測定条件

ウォームアップ30秒＋測定120秒を初期手順とし、盤面、個数、解像度、DPR、品質、端末、ブラウザ、ビルド種別を記録する。1→5→12→24個、M4で60個と分離後の状態を測る。途中で品質を変えた値を一つの結果へ混ぜない。

requestAnimationFrameの間隔は画面更新の指標で、GPU描画時間や指から画面までの完全な遅延値ではない。ヘッドレスやソフトウェア描画の結果を実機GPUの結果として扱わない。

### 11.3 品質調整と異常時

内部解像度、DPR上限、表面解像度、透過処理解像度、集光模様などを段階的に調整する。画質設定で物理速度・融合・色成分・判定個数を変えない。見えない雫だけ衝突に残すことを禁止する。

GPUリソース、RAF、イベントを破棄し、タブ非表示・復帰・描画コンテキスト喪失を安全に扱う。非対応時に無言の黒画面を出さず、状態と再試行手段を示す。旧描画へ退避できても、それを高品質版の合格とは扱わない。

## 13. 受け入れ条件と評価責任

詳細手順は `VALIDATION.md`。結果は実施済み／未実施／失敗／確認待ちを明示する。

**自動検査**は型、起動、数値の保存、イベント順、入力状態、回帰を担当する。**実ブラウザ**で透明体の描画と応答・性能を確認する。**RYO**が水滴らしさ、融合の快感、もう一度触りたくなるかを判断する。

特に重視する受け入れ場面は、掴み中の連続融合、高速で小さな雫を通過する吸収、異色の反発と混色の違い、分離直後の再操作、最大数での見え方、無音の初回利用。

初見の利用者数名に、事前説明なしで操作を始められるか、融合後に自発的に再操作するか、邪魔に感じるUIがあるかを観察するのも有用。これは開発中の定性評価であり、市場需要や継続率の統計的証明ではない。行動を成功させるために試験中に誘導しない。

## 16. Codexでの運用

作業の中心はCodex。チャットとの往復を必須にしない。開始時に適用される `AGENTS.md` と `STATUS.md`、今回対象の要件を読む。中程度以上の変更は短い実行計画を作ってから、小さな変更→検証→実画面確認→記録の順で進める。[O1][O2]

依存追加は既存のパッケージ管理方式を尊重し、選定した版とロックファイルを記録する。基準ソースにはロックファイルとtest/typecheckスクリプトが見当たらないため、存在しない `npm ci` や `npm test` がそのまま使えると仮定しない。[B1][B6]

毎回の終了時に、変更内容、実行コマンドと結果、起動方法、スクリーンショット／動画の有無、計測条件、未検証、品質判断待ち、次の一手を `STATUS.md` へ残す。自分が実装したという理由だけで人の感覚評価まで承認済みにしない。

`AGENTS.md` は短い共通指示と参照先を置くために使い、全要件を貼り込まない。適用される既存の指示・権限・確認ルールを維持する。GitHubへのpush、公開、デプロイは今回の開始指示に含めない。
